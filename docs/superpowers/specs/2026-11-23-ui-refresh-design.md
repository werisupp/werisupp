# サイト全体の見た目と導線の一新（2026-11-23）

ウェリサポのサイト（`index.html`・`step1〜16.html`・`about.html`・`tool/`）の見た目と導線を作り直すための設計書。
ホストと合意した内容をまとめたもの。「作る人の判断」と書いたところは、ホストが決めたことではなく、この設計を書いた側の判断。

## 1. 目的となぜ

- サイトを再び動かすにあたり、想定する読者にとって **使いやすく・理解しやすく・見やすい** 見た目に一新する。
- いまの見た目は以前のAIツールで作ったもので、よくある「青いグラデーション＋大きな見出し帯＋枠付きボックスだらけ」になっている。読者が疲れているときに読み進めにくい。

## 2. 誰が・どう読むか

- **読者**: 上司との関係や職場の環境で消耗していて、転職したいのに動けていない会社員。転職活動は初めてのことが多い。
- **読まれ方**（作る人の想定）: X の投稿から記事に来る人が中心なので、**スマホで、夜や移動中に、疲れた状態で** 読む。1記事を読み切らずに離れ、後日続きから読むことも多い。
- だから大事にすること:
  1. 開いてすぐ「何のページで、自分はいまどこにいるか」が分かる（STEP ③ / 16 のような位置）。
  2. 読み終えたら「次に何をすればいいか」が1つだけはっきり見える（次のSTEPへ）。
  3. 長い記事でも圧迫感がない（文字が読みやすく、強調が多すぎない）。

## 3. ゴール・やらないこと・失敗とみなすこと

**ゴール**
- 全ページを新しい見た目（§5）にそろえる。
- 全ページに共通の導線（§6）を入れる: STEPの題名が分かるメニュー、記事上部の位置表示、記事下部の「次のSTEPへ」。
- サイドバーやメニューのHTMLを各ページに複製するのをやめ、`common.js` の1か所の一覧から組み立てる（ページを足すときの手間とずれをなくす）。
- 各ページに直接書かれた見た目の指定（`style="…"`。STEP3・6・7で約145か所）を共通の部品（`style.css` のクラス）に置き換える。

**やらないこと**
- **記事の本文を変えない。** 文章の追加・削除・言い換え・順番の入れ替えをしない（ホストと合意。本文の見直しは、反応を見てから記事ごとに別で行う）。
  - 例外として、ナビゲーションやボタンの短い文言（「次のSTEPへ」「メニュー」「この記事の内容」「準備中」など）は新しく書いてよい。
- ビルドの仕組み（静的サイトジェネレーター、npm のビルドなど）を入れない（AGENTS.md）。
- ダークモード（作る人の判断。記事内の画像が白背景で暗い画面に合わないため。色は変数にまとめておき、後から足せるようにする）。
- 画像（`image/`）の作り直し。

**失敗とみなすこと（見た目が良くなっても避ける）**
- 本文の文章がどこか1か所でも変わっている、または消えている。
- PR表記（サイト上部の表記・リンク近くの「PR」）が消える、または見えにくくなる。
- スマホ幅（375px）で横にはみ出す、文字が小さすぎる（本文16px未満）、ボタンが押しにくい（高さ44px未満）。
  - → 本文16px以上は10章で変更（ボックスの中の文字）。
- 計測の口（`data-track` 属性と `common.js` の計測処理）が壊れる。
- 無料ツールの入力内容がブラウザの外に送られるようになる。

## 4. 制約

- 静的サイト（HTML・CSS・JavaScript のみ、ビルドなし）。本番は Cloudflare Pages、`main` へのマージ＝公開。
- リポジトリは公開。個人を特定できる情報や内部メモを書かない（AGENTS.md）。
- 共通の見た目は `style.css`、共通の動きは `common.js` に置き、ページごとに複製しない（AGENTS.md）。無料ツールは `tool/tool.css` と `tool/tool-ui.js` を持っているので、ツール独自の部分はそこに残してよい。
- 外部の読み込みを増やさない（作る人の判断）。Webフォントは使わず、端末の日本語フォントを使う（日本語のWebフォントは重く、疲れた読者を待たせるため）。
- **進行中のPR**: STEP⑩（PR #11）と STEP⑪（PR #12）が `step10〜16.html` を変更中でレビュー待ち。`step10〜16.html` の作り替えは最後に回し、その時点の `main` に対して行う（§8）。

### 5-3. 部品（今あるクラス名を残し、見た目だけ変える）

本文の中の部品は、今のクラス名のまま新しい見た目にする（HTMLの書き換えを最小にするため）。主なもの:

## 8. 進め方

### 8-1. 比べた案と選んだもの

**本文に手を入れるか**（ホストが A を選択）
- A. 見た目と導線だけ直す（本文は変えない）: 確認は見た目だけで済み、早く出せる。 ← **選択**
- B. 本文の構成も見直す: 読みやすさはさらに上がるが、記事ごとにホストの内容確認が必要で時間がかかる。A のあと、反応を見て記事ごとに行う。

**作り方**（作る人の判断。ホストにも提示済み）
- 共通の CSS・JS を作り直し、HTML の変更は最小にする ← **選択**。本文を誤って変える危険が小さく、進行中のPRとも重なりにくい。
- 全ページのHTMLを新しい作りで書き直す: HTML はきれいになるが、変更が数千行になって本文の取りこぼしを確かめにくく、PR #11・#12 と必ず衝突する。見送り。
- ビルドの仕組みを入れる: AGENTS.md の「ビルドなし」に反する。見送り。

### 8-2. 順番と公開のしかた

1. **土台と見本**: `style.css` の作り直し、`common.js` の導線（6章）、見本として `index.html` と `step3.html` を仕上げる。
2. **ホストの確認①**: 見本をプレビューURLで見てもらい、方向を確定する。
3. **残りのページ**: step1・2・4〜9、about、tool/ を並行で進める。
4. **step10〜16**: PR #11・#12 のマージ後の `main` を取り込んでから行う。
   - マージされていなければ、その時点の `main` の版（雛形）に対して行う。
   - そのあと #11・#12 をマージするときは、`claude/ui-refresh` を先に `main` へ出してから、#11・#12 のブランチに `main` を取り込む。衝突するのはサイドバーなどの共通部分だけで、#11・#12 の本文は残す。これは窓口が行う。
5. **ホストの確認②**: 全ページをプレビューで確認してもらい、`main` にマージする（＝公開）。

- 作業は統合用のブランチ `claude/ui-refresh` に集め、各作業はそこから切ったブランチで行って `claude/ui-refresh` へのPRで渡す。公開は最後の `claude/ui-refresh` → `main` の1回だけ。途中で新旧の見た目が混ざった状態を公開しない。

### 8-3. 確かめ方（各作業の完了条件）

- **本文が変わっていないこと**: 作業前と作業後で、各ページの本文を取り出して比べ、一致すること。比べるスクリプトはリポジトリに置き、誰でも同じ確認ができるようにする。
  - 本文に含めるもの: `main` 要素の中の文字。見出し帯（h1・`step-meta`）も含める。
  - 比べる対象から外すもの: 導線として置き換えると決めた部分だけ。6-5 の「← 脱出ガイド一覧に戻る」、`final-cta` の中のSTEPや一覧へのリンク、目次の中身（自動生成）、準備中ページの雛形の文。
  - 外すものはスクリプトの中に一覧で書き、それ以外の差は1文字でも失敗にする。
  - 比べるときは空白と改行の違いを無視してよい。
- **画面**: 変更した各ページを、スマホ幅375pxとPC幅1280pxでスクリーンショットに撮り、PRに貼る。375pxで横にはみ出さないことを確かめる。
- **リンク**: メニュー・前後のSTEP・目次のリンクがすべて存在するページを指していること。
- **計測とPR表記**: `data-track` 属性が残っていること。PR表記が全ページに出ていること。
- **ツール**: 既存のテスト（`tests/tool-core.test.mjs`）が通ること。
